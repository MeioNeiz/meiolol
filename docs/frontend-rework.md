# Front end rework: survey and options (21 Oct 2026)

Read-only survey of src/site, src/site/static, src/tpl, the render server and the desktop
window, to scope the rework in docs/plan.md "Now" item 3. Line numbers are at 553b5fa.

## Short version

- The HTML side is better than it feels. src/tpl is a real compile-time checked template
  engine (escaping by context, tag balance, hole/field typos are compile errors). The pain
  is not templating; it is that there is no layer above it: no shared components, no
  asset registry, and two other render paths (hand-built DOM in JS, and JS copies of Zig
  logic) that know nothing of the Zig one.
- The site is three front ends in one: Zig SSR stats pages; skeleton pages that JS fills
  by id (Your games, Daily Draft, Learn, Pool, home demo); and the champion page, where
  filters.js re-renders the Zig table in JS with hand-copied maths.
- JS has no module system or shared core: 5 `el()` helpers, 3 `getJson`, 5 role tables,
  4 `pct`, 4 `signed` that disagree on the minus sign; globals and load order live in
  Zig string literals.
- CSS has colour tokens and nothing else: 25 font sizes, 13 radii, 9 breakpoints, four
  look-alike card surfaces, 95 class names of 1-3 letters, page prefixes for the rest.
- Nothing runs the JS or measures layout in tests. Every phone overflow and every "JS
  can't find its DOM" bug so far was found by hand (QA passes, Jacob, reviewers).
- The desktop app shares nothing with the site: dvui immediate mode, its own theme,
  colours and a third lane chart. Site CSS/JS cannot be what slows the app today; but a
  shared component layer is the only route to one UI for both later.
- Recommendation: Option A below (Zig component layer, CSS tokens and layers, one JS
  core bundled by concatenation, hashed assets, Zig components in wasm for the redraws,
  a browser QA script). About 8-10 days of foundation, then pages move as the planned
  design work touches them.

### Zero JS is not possible; all feature code in Zig is

- No browser lets wasm touch the DOM, and no proposal would change that; a JS loader is
  the floor. Zig 0.17's externref is half-working and goes in 0.18.
- zjb (Zig to JS bridge, MIT, ~1,000 lines, upstream quiet since April) builds on 0.17
  after a two-call-site patch (@typeInfo `field_types`/`param_types`). Spike
  (research/raw/zjb-tpl-island-spike.md): a filter-like island in Zig with our own tpl,
  rank click re-sums and re-renders, localStorage, fetch, escaping intact; 6.0 KB gz
  wasm + 0.9 KB gz generated glue; the only hand-written JS a 5-line loader.
- The inventory (docs/js-inventory.md): of 4,887 public lines, ~48% is work Zig should
  do on the server anyway, 13% plain HTML/CSS, 6% client maths, 33% glue.
- So, by feature:
  - Pages and no-JS fallbacks: tpl components rendered by `meiolol render`, as now
  - Interactions (filters, review moments, Daily, Learn, search, sort, storage, polling):
    the same tpl components compiled into one shared `ui.wasm`, driven through zjb.
    One component, two places: the filters.js twins (the worst bug class here) go by
    construction, and clicks need no round trip
  - Big data (Pool's 1.9M player tallies): fragments from `meiolol render`, fetched and
    swapped by the Zig runtime
  - Dialogs, popovers, accordions: HTML only (`commandfor`, `popover`, `details name`,
    Safari 26.2+); no radio or `:has()` state hacks (fail WCAG 4.1.2)
  - Hand-written JS: the loader. Glue is generated by zjb from the wasm
- Work: vendor the zjb fork as a path dependency (deps/zjb), its generator in `zig build`;
  a thin `dom.zig` over it (byId, setHtml from a tpl component, on(event), fetchText,
  storage) so pages never touch handles; a test that the handle count stays flat; hashed
  `ui.wasm` (budget 40 KB gz).
- Risks: we own the fork (each Zig release may break it; today's fix took 10 lines);
  release wasm traps without a stack trace (zjb's panic logs the message); spike not
  yet run on Safari/iOS or a phone; shipping data the client re-sums (filters JSON is
  183 KB gz today; a binary form would be smaller).
- Changes to Option A: step 4 (one JS core) becomes `dom.zig` on zjb; step 5 (wasm
  redraws) grows to every interaction; steps 1-3, 6, 7 stand. First check: the spike
  on iPhone Safari.

## 1. How a page is produced

### Writing HTML

- `src/tpl/root.zig` (821 lines, own build module, std only): `tpl.render(w, comptime
  src, args)` parses the template at compile time; holes are named, every hole needs a
  field and every field a hole; escaping by position (text, attribute, URL with scheme
  check, on*/style, script/style); `render` must balance tags, `renderPart` may not
  (layout pieces). Values: strings, numbers with fmt options, optionals, `t()` nested
  templates, `call(fn, args)`, `each(items, ctx, fn)`, `when(cond, v)`, `trusted`,
  `json`, `attr`, `flag`, and any struct with `render(self, w)` (a component).
  compile_errors.zig holds 31 templates that must fail to compile, run by `zig build
  tpl-errors`.
- Moved onto tpl 12-13 Oct, page by page, byte-identical (2b5d291, 203f4f5, d27fe85,
  6c0079c...). Usage now: ~270 render/t/renderPart calls, 98 `tpl.call`, 7 `tpl.each`,
  59 `tpl.when`, 11 `tpl.trusted`.
- Still raw writer calls for markup in places: builds.zig rune pages (47 `writeAll` of
  `<div class="rr">` etc., builds.zig:375-523), html.zig:329 `minGames` (w.print of
  `<select data-key="{s}"`, unescaped, key is program text), root.zig:509 role icon
  symbols, tierlist.zig:106 and 199, pool.zig:93, matchup.zig:154-189. src/admin.zig is
  all `w.print` (private page).
- Page shape: every page function calls `html.head(w, Page)` then writes its body then
  `html.foot` (html.zig:136, 303). `Page` (html.zig:96) carries title, nav, view and
  counterparts for the region/period switches. Pages are functions of (path, Site);
  `root.renderPage` and `renderShared` route (root.zig:385, 420).
- Templates are long single lines: 59 lines over 200 chars in src/site/*.zig, two over
  1,000 (champion.zig:91, tierlist.zig). Example, champion.zig:91 (cut):

      <div class="tiles"><div data-tile="wr"><span>Win rate</span><b class="wrc"
      style="--c:{colour};opacity:{fade:.2}">{wr}</b><small data-rank>{rank}{won}</small>
      </div><div data-tile="pick"><span>Pick rate</span>...

### Escaping

- Inside tpl: by context, compile-time checked, URL scheme checked at run time.
- Outside tpl: whatever the writer call does (nothing). Safe today because those calls
  write program constants and numbers, but nothing enforces it.
- JS side: `textContent` almost everywhere (good). innerHTML in filters.js (10 uses:
  snapshot/restore of server markup, and template strings of numbers in trackCell,
  filters.js:356-367) and review.js:188; chart.wasm SVG goes in as markup, trusted
  because tpl escaped the names in Zig (review.js:467-470).

### Data to JS

Four channels, chosen per page:

1. data- attributes on server markup: filters.js (22 `dataset.` reads), table.js (16),
   min-games.js (9), learn.js (16); `data-site`, `data-view`, `data-root` on script tags
   (html.zig:176, home.zig:76).
2. Inline JSON: only learn.zig:229-235, `<script type="application/json">` via `tpl.json`.
3. Fetched JSON: data/champions.json (fetched separately by review.js:50, pool.js:34,
   your.js:697, learn.js), data/pool.json, data/learning.json, data/search.json,
   data/filters/<slug>.json, daily/<n>.json, learn/practice.json, the Your games API.
   JSON is hand-written in Zig with writeAll (champs.zig:106-122, filters.zig:451-557).
4. Binary plus wasm: meiolol.wasm and patch/data/stats.bin for Learn's scorer
   (learn.js:529-531); chart.wasm renders lanechart.zig's SVG in the browser for Your
   games (chart_wasm.zig, a hand-packed little-endian input, no JSON).

Point 4 matters: the repo already runs a tpl component (lanechart.zig) in the browser
through wasm. That is the cheapest route to removing JS copies of Zig markup.

### Static assets

- Embedded with `@embedFile` (root.zig:280-298): style.css, favicon, inter.woff2 and 11
  JS files at the site root, pool.js and min-games.js again in every view directory.
- No fingerprinting: pages link `style.css`, `../table.js` by fixed name. nginx serves
  them `Cache-Control: no-cache` (docs/backlog.md:403); the renderer serves its own
  files no-cache too (serve.zig:268), rendered pages `max-age=3600` (serve.zig:373).
- No build step: no minify, no bundling, no transpile. Script tags are hand-written in
  each page module with hand-made relative paths: champion.zig:130 `"../table.js"`,
  tierlist.zig:340 `{table_js}`, learning.zig:169 `{up}table.js`, daily.zig:55, your.zig:71.
- Inline scripts in html.zig: localStorage view memory (head), `admin_link`
  (html.zig:198) and `meio_view` (html.zig:206) as JS in Zig strings.
- Sizes are fine: style.css 77 KB (16 KB gzip), largest page script review.js 41 KB
  (14 KB gzip), font 48 KB. Weight is not a problem to solve.

## 4. JS coupling to the Zig DOM, build steps, checks

- Skeleton pages are id-driven: your.js 48 id lookups, learn.js 38, daily.js 24 against
  the skeletons in your.zig, learn.zig, daily.zig. All ids they read exist today (checked
  by script: the three not in the skeletons, `recent`, `example-roles`, `back`, are made
  by the JS itself), but nothing checks it.
- Enhancement scripts are selector-driven: filters.js 32 querySelector calls (section
  ids, `.tiles`, `[data-tile]`, `.tl-more`, `[data-show-all]`, `[data-reset]`), table.js
  and min-games.js by data- attributes.
- Shared code is by globals and order: review.js defines `Review` (review.js:7) for
  your.js and home.js; reasons.js defines `detectedReason`/`reasonWords` for daily.js and
  learn.js. Order is the order of the `<script>` lines in your.zig:71, home.zig:75,
  daily.zig:55, learn.zig:232. Classic scripts with "use strict", no ES modules.
- Build: none. `@embedFile` and serve. CI: `node --check` per file (build.zig:159), a
  syntax check only. No lint, no type check, no run.
- Dev loop is good: `meiolol dev` serves CSS/JS from disk and reloads on edit; a Zig
  template edit is ~20 s (architecture.md "Website").

## 5. Tests

What pipeline_test and the site tests check (src/pipeline_test.zig, 26 tests in
src/site/*.zig):

- Golden hashes of every generated non-asset file (expectSiteFiles, pipeline_test:910,
  src/testdata/site-files.txt, 151 files). commit.sh rewrites it on every commit, so it
  says "these pages changed", never what changed. It is what made the tpl migration
  provably byte-identical; it will do the same for a component refactor.
- Substring contracts: ~40 exact markup fragments per page type (pipeline_test:186-242),
  e.g. `<div class="tiles mu-tiles">`, `<tr class="bx thin" data-id=`. Brittle by design:
  any class rename means editing these.
- DOM contracts, two only: every `data-filter`/`data-for`/... target id exists
  (pipeline_test:271-300, after 0406809), and no `data-sortable` page without table.js
  (:314, after 553b5fa). Both added after the bug.
- Static build equals rendered-on-request bytes for every file (:303-320), views file
  round trips, `--static core` lists.
- write.zig:190-214: view links, switches, script tags.

Impossible now:

- Running any page's JS (no DOM in tests): Your games, Daily, Learn, Pool, filters.js
  redraw, search, review are untested apart from `node --check`.
- Checking that filters.js's redraw equals the Zig rendering.
- Layout: overflow at 390 px, text size, overlap; QA is manual through `browse`
  (docs/plan/site.md:35, :294, :305). The night run already had a Playwright script for
  design measurement (data/team/2026-10-19-night/design-proto.mjs, using

- Desktop: `desktop-shot` renders PNGs (good), no assertions on them.

## 6. Constraints any rework must keep

- Zig-only native code; JS and CSS are already shipped, so "Zig-only" constrains tools,
  not the browser. No Node build step in the shipped path (CI's `node --check` is the
  only Node use).
- Static nginx core plus `meiolol render` with byte-identical output between the two
  (pipeline_test). The home page must stay static (hosting.md "Rendering on request").
- No external scripts or fonts: confirmed. The only third-party host is Data Dragon for
  champion and profile icons (10 references), with `referrer: no-referrer` (html.zig:136).
- Traffic counting depends on `/style.css` being fetched on every page load
  (traffic.sh:8-12, no-cache). Hashed immutable CSS breaks it unless a tiny no-cache
  beacon replaces it.
- Deploys: the renderer swap waits for the upload because asset names don't change
  (render-swap.sh:9-12). Hashed names plus the renderer serving its own assets as
  nginx's fallback removes the wait.
- Product rules (production-key.md): no "+X% win rate", several options with reasons.
  Content, not structure, but components with fixed wording help keep it.
- Preview mode, noindex, the banner, privacy (no names in champ select views).
- Pages must work without JS where they do today (stats pages, lookup form fallback).
- Many sessions edit the tree at once: a big-bang rewrite would conflict with every
  in-flight page change. Migration must be page by page, each commit small.

  That is a dashboard-sized UI; in dvui each layout, icon and table is hand-placed Zig.
- So: the site's CSS/JS/templates are not what slows app work today. If Jacob's "app
  development" means the desktop, the pain there is dvui, a separate decision. If it
  means the site as a web app, it is the rest of this document. Worth asking him.

## Rework options

### Option A: Zig component layer, CSS tokens and layers, one JS core (recommended)

What:

1. Hashed assets (0.5-1 day). At load, hash each embedded asset and serve it as
   `style.<hash>.css`, `table.<hash>.js`; `html.Page` links by logical name. Uploads
   keep old hashed files for a day; nginx falls back to the renderer for a missing one,
   and the renderer serves its own embedded copy, so render-swap.sh no longer waits for
   the upload. Assets get `immutable`; a 0-byte no-cache `/v.css` (or the current
   `/style.css` kept as a stub) keeps traffic.sh counting.
2. CSS foundation (1-1.5 days). Split style.css into static/css/tokens.css, base.css,
   components.css and one file per page, concatenated in Zig at comptime into the one
   served file (no tool). `@layer tokens, base, components, pages` ends specificity
   fights. Add spacing, type and radius scales (e.g. 4/8/12/16/24; 11/12/13/14/16/22;
   6/10/14) and three breakpoints (480, 760, 1000). A Zig test lints the CSS: no hex
   outside tokens.css, no @media width outside the three, no font-size outside the
   scale (allow-list for exceptions with a comment).
3. Components (2-3 days). src/site/ui.zig: structs with `render(self, w)` on tpl:
   `Tile`/`Tiles`, one `Card` with variants (replaces card, panel, mu-card, tiles >
   div), `SectionHead`, `Tabs`, `Segmented`, `Table` (sortable, searchable, min-games;
   registers its script), `ChampLink` (exists in root.zig), `WrCell`/`TrackCell`,
   `GoldCell`, `Legend`, `Note`. Class names per component (`.c-tile`, `.c-card`...);
   short names stay scoped inside one component. `Page` gains a script set:
   components add what they need, `html.foot` writes each once, in dependency order. A
   test fails on any `<script src` written outside html.zig.
4. One JS core (1.5-2 days). static/js/core.js: `h()` (one el signature), `$`, fetch
   helpers, `champions()` loader (one fetch of champions.json, cached), icon URLs, role
   table, one set of formatters (`signed` with U+2212 or "-", decided once, `pct`,
   `thousands`, `points`) matching Zig's. Zig concatenates `core.js ++ page.js` per
   page bundle at comptime inside an IIFE: modules without a bundler, and `Review`,
   `reasons` stop being globals. A small `mount(el, state, render)` helper for
   interactive pages so state lives outside render (the c7f4003 class).
5. Zig components in wasm for redraws (2-3 days). Grow chart.wasm into ui.wasm: export
   the opponent row, tiles and win rate cell from ui.zig, as chart_wasm.zig does for
   lanechart.zig (tpl needs no allocator). filters.js then sums its slices and asks
   wasm for markup: the JS copies of trackCell, usualCell, goldCell, usual, points,
   wrColour and fade go. A test renders a row both ways from the same numbers. Your
   games' review panels can follow later.
6. Checks (1-1.5 days). (a) Zig test: every `$("id")`/`querySelector` literal in a
   page's JS bundle exists in that page's output or is created by the JS (explicit
   allow-list). (b) deploy/qa.sh with the existing Playwright: every page type from
   `meiolol dev` at 390 and 1280 px, fail on console errors, failed requests,
   `scrollWidth > innerWidth`, text under 11 px. Run before pushing UI work; not in
   pre-push ci unless Chrome is there.
7. Migration, page by page, each first byte-identical (site-files.txt unchanged), then
   the visual change as its own commit: champion page (design build order step 4,
   and the filters.js twin), champions index (5), header (6), matchup (8), Your games and
   review (9), Daily Draft, Learn (its redesign, docs/learn-proposal.md, built on the new
   pieces), then pool, patch, builds, prose, admin last. 0.5-1 day a page type, mostly
   folded into design work already planned.

Fixes: duplicated markup and CSS drift, the script-loading and id-coupling bug classes
(by construction plus tests), Zig/JS twin logic, formatting drift, phone overflow found
by a script instead of a person, the deploy wait. Keeps everything that works: tpl,
SSR, byte-identical static and rendered output, no build tool.

Cost: foundation 8-10 days (1-6), migration 6-8 days spread over the design work.

Risks: a component API that is too rigid for dense one-off cards (keep an escape hatch:
pages may still write tpl directly with tokens); site-files.txt churn while sessions
work in parallel (do the CSS split and core.js on a quiet day, announce in the run's
common.md); wasm size (chart.wasm 12 KB today; budget 40 KB); hashed assets need the
nginx fallback rule on jomify (`deploy/jomify.sh install`), a hand-installed piece.

For the app: ui.zig components render HTML from plain data with no allocator, so a
future WebView2 desktop could render them natively in Zig and reuse style.css. This is
the only option that keeps that door open without a JS framework.

### Option B: a template language compiled at build time

What: templates in .html files with loops and conditionals in the template (`{#each}`,
`{#if}`), compiled to Zig by tpl's comptime parser or a build step.

- The cheap half is nearly free: tpl parses comptime strings, so `tpl.render(w,
  @embedFile("tpl/champion-tiles.html"), args)` works today (0.5 day to adopt and
  document). It gives editor highlighting and short Zig functions.
- The full language (blocks, partials, imports) is 3-5 days of tpl work plus migration,
  8-12 days total.

Fixes: readability of long one-line templates. Does not fix JS duplication, the
Zig/JS twins, CSS drift, script loading, tests or the deploy wait. Moves logic into a
second language that Zig's type checks see less of.

Recommend only the cheap half, inside Option A, for big static blocks (home, prose,
skeletons).

### Option C: client-rendered interactive pages with a tiny own framework

What: a ~300-line no-dependency `h()` plus keyed re-render and small signals, vendored;
Your games, Daily Draft, Learn, Pool, the home demo and the champion filters become JS
components; stats pages stay Zig SSR for search engines, Riot's reviewers and no-JS.
Optionally later: the desktop moves to a WebView2 window that hosts the same JS UI.

Fixes: hand DOM building, state lost on re-render, skeleton id coupling (the component
owns its DOM).

Does not fix, or worsens: two component systems remain (Zig SSR and JS), so tiles and
tables still exist twice, and the Zig/JS twin logic grows unless SSR pages also render
in JS, which costs SEO and no-JS and the byte-identical render tests. CSS untouched.

Cost: 2-3 days framework, 8-12 days porting; WebView2 desktop another 5-10 (COM from
Zig, a Windows runtime dependency, ~100 MB more memory, a new update path).

Risks: the largest rewrite, conflicts with every in-flight page change, and a second
UI stack to maintain. Take one idea from it into A: the `mount(state, render)` helper.

## Recommendation

Option A, with B's file templates where a block is long and static, and C's state
helper for the interactive pages. Order: hashed assets and the QA script first (they
pay off at once and catch regressions during the rest), then CSS split and tokens, then
ui.zig plus core.js on the champion page (it exercises every piece: tiles, table,
filters redraw, wasm), then the other pages as design build order steps 4-9 reach them.
Decide the desktop's toolkit separately, after a 1-2 day WebView2 spike against dvui
for Jacob's champ select list; A's components would serve either answer.

## Pain that is not structural

- Design decisions (density, what colour means, what hides on a phone) are design work;
  docs/design-ideas.md already has the rules. Components make them stick, they don't
  make them.
- Velocity: 250 site commits in 10 days from many sessions. Drift follows from that in
  any stack; components and lints only lower its cost.
- Copy and policy wording (no win chance numbers, "few games") is content.
- tpl itself is good and the dev loop is fast for CSS and JS; Zig template edits are
  ~20 s, which no option here changes much.
- Phone overflow on dense tables is partly inherent: a rule per table of which columns
  fold at 480 px is needed whatever renders them.
- Dead CSS is negligible (about three rule groups).

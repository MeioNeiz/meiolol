# Talk: Introducing Ghostty and Some Useful Zig Patterns (Mitchell Hashimoto)

Why: what Zig patterns does Ghostty's author pick out as the ones that matter?

## Assessment

- Evidence: B. First-hand report by the author of [[ghostty-repo]] (A), Sept 2023, Zig ~0.11;
  the patterns are still in the code at 0.17 (comptime backends, data tables).
- Reasoning: fair. Gives benefits and one cost each (test all build options, @Type harms
  readability and compile time) but the code is on slides missing from the text.
- Interests: promoting Ghostty, then in closed beta.
- Weigh: patterns trustworthy (confirmed in the repo); `@Type` is gone in 0.17 (now `@Enum`,
  `@Union`, `@Int` etc., see [[ghostty-repo#^f46]]).

## Findings

- [zig/comptime] Comptime interfaces: a value whose implementation is picked from compile-time information (font face: CoreText, FreeType or web Canvas). ^f1
  > A comptime interface is a value with an implementation that changes depending on some compile-time-known information.
- [zig/comptime] Main benefit: zero runtime overhead for implementations that never change at runtime; field access and dispatch resolved at compile time. ^f2
  > The main benefit is for implementations that _never_ change at runtime you can swap out implementations with zero runtime overhead.
- [zig/comptime] [zig/test] Cost: Zig analyses only referenced code, so an unbuilt backend can rot; Ghostty builds every option in CI. ^f3
  > The downside is for comptime interfaces, you must ensure you test all build options otherwise it is very easy to introduce build failures.
  > Ghostty runs through all build options in CI.
- [zig/comptime] Lazy analysis is a feature: situational code needs no ifdef-style guards. ^f4
  > it enables situational code to exist without nasty `#ifdef`\-style guards to make it invisible.
- [zig/comptime] Data tables: a non-pub raw tuple table, easy to edit, is converted at comptime into runtime-friendly structs; raw entries take no binary space. ^f5
  > The conversion process happens all at compile-time, so there is no runtime cost.
  > since the raw entries aren't ever used in runtime code, they don't take up any binary space in your final build.
- [zig/comptime] Platform-specific tables keep only the target's column at comptime (smaller struct and binary, no runtime lookup). ^f6
  > But for runtime we turn it into `entries` which contains only the platform we're building for.
- [zig/comptime] Repetitive tables are generated by a function run at comptime instead of shell or Python codegen scripts. ^f7
  > Many projects often have shell, Python, or other scripts to do data generation. With Zig, you can do it all in comptime.
- [zig/comptime] Wrapping a function body in `comptime {}` makes it impossible to call at runtime. ^f8
  > is a trick to ensure that this function can never be called at runtime.
- [zig/comptime] Type generation (`@Type` then) is powerful but should be limited: it harms readability and slows compilation. ^f9
  > You need to be careful to not go "full metaprogramming" because it harms readability and slows down compilation.
- [zig/comptime] Ghostty generates the modes enum from an entries table so each mode's extra data stays packed next to its name. ^f10
  > The reason I don't define the enum up front is because there is additional data associated with each entry that I want to keep packed for easy editing and reference.
- [zig/perf] [zig/test] FontIndex derives its index bit width from the style bits; tests pin the size so widening is a conscious act. ^f11
  > this is paired with tests to ensure we have a specific size available so that if we do ever increase the bitsize of Style, we are doing it very consciously.
- [zig/build] [zig/api] The same Zig program builds as an exe (Linux, GTK) and as a static lib with a C API that the Swift macOS app calls. ^f12
  > I compile this into a static library that my Swift-based macOS app depends on, and Swift then calls the library.
  > how easy Zig made it (the Zig build system in particular) to write a program that can compile as both an exe and a lib.
- [zig/memory] He admits memory use lagged CPU work, e.g. preallocating the whole scrollback; later pages are allocated on demand ([[ghostty-repo#^f22]]). ^f13
  > I spent a lot of time and effort ensuring CPU and renderer performance was great, but was a little lax on memory usage.
- [zig/test] Fuzzing the VT parser was planned after early fuzzing found bugs; it now exists as AFL++ harnesses ([[ghostty-repo#^f69]]). ^f14
  > We did some fuzzing and found a few bugs so I'm sure there are plenty more lurking around.
- [toolchain] (inferred) Written for Zig ~0.11 (Sept 2023); `@Type` advice is stale for 0.17, which replaced it with per-kind builtins. ^f15

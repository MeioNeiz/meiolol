# Zig Build System Internals (Mitchell Hashimoto)

Why: what mental model of `zig build` avoids common build.zig mistakes?

## Assessment

- Evidence: B. Careful read of the Zig source at the time by a later Zig contributor.
- Reasoning: fair. Clear model and one practical pitfall (declarative vs imperative).
- Interests: none.
- Weigh: written for Zig ~0.9: `std.build.Builder`, `LibExeObjStep`, `lib/std/special/
  build_runner.zig`, `--pkg-begin` and the `makeOneStep` code are all gone. Keep only the
  model: a compiled build program, a declared step graph, steps that run later. Check
  details against [[zig-learn-build-system]] and the 0.17 std.

## Findings

- [zig/build] `zig build` compiles build.zig into a cached build binary, then runs it; the build binary shells out to the compiler for each artifact. ^f1
  > it first compiles a build binary and then that build binary subsequently compiles your project code.
  > The build binary does not embed a Zig compiler; it further subprocesses to the Zig compiler to build individual artifacts as necessary.
- [zig/build] build() only declares steps and dependencies; nothing runs until the runner executes the graph. ^f2
  > The `build` function defines the set of steps and their dependencies, but _does not execute them_.
- [zig/build] Pitfall: reading a file a step generates must happen inside a step's make function, not in build(). ^f3
  > If you have a step that reads a file that is generated by a previous step, then that must be done using a custom step with the `makeFn`.
- [zig/build] Steps over files that exist before the build should be created in build() so the graph is complete. ^f4
  > you can (and likely should) do that directly in the `build` function so that the steps are fully defined.
- [zig/build] build.zig is ordinary Zig compiled for the host, so anything is possible there. ^f5
  > My primary takeaway from studying the internals of the Zig build system is that _its just Zig_.
- [zig/comptime] The runner accepted `build` returning void or any error union by inspecting its type at comptime. ^f6
  > The build runner uses Zig's [comptime capabilities](https://ziglang.org/documentation/master/#comptime) to introspect on the function signature
- [toolchain] (inferred) Every API name in the post (`std.build.Builder`, `LibExeObjStep`, `--pkg-begin`) predates 0.11; treat code as history. ^f7
